# Bangarr — Agent Guide

Commit only when explicitly asked. Use Conventional Commits. Before committing, run `bun check`, `bun typecheck`, `bun test`, and `bun run build` from the repository root. Do not add `biome-ignore` directives.

## Scope and workflow

- Read current source, scripts, configuration and relevant docs before editing. Keep changes within the requested scope; a module cleanup does not authorize reorganizing the whole application.
- Focus on Plex → Bangumi synchronization. Do not add peripheral features, compatibility layers or generic infrastructure without a concrete requirement.
- Use reference projects for the requested conventions, not as templates for the entire directory tree or runtime. This is a self-hosted Bun application, not a Cloudflare Worker.
- Preserve existing user data and secrets. Do not introduce migrations for speculative compatibility, or delete databases to make a schema change work.
- Update user-facing documentation when behavior or configuration changes. Keep UI, validation and runtime defaults consistent; document environment-only settings in `.env.example`.

## Backend modules

Use these file roles inside each feature module; create only the files the feature needs:

| File | Responsibility |
| --- | --- |
| `index.ts` | Elysia controller: routes and thin handlers |
| `model.ts` | Request and response schemas |
| `types.ts` | Types that cannot be derived from schemas |
| `errors.ts` | Feature-specific error classes |
| `service.ts` | Business orchestration across persistence and external clients |
| `utils.ts` | Pure parsing, formatting and calculation helpers |

- Non-request-dependent services use `abstract class XxxService` with static methods and explicit dependencies. Do not create a service instance registry.
- Request-dependent authentication and context handling belong in Elysia plugins. The plugin is the service; do not add another `service.ts` inside it.
- A large `utils.ts` may become `utils/` with purpose-named files. Do not scatter business logic into arbitrary sibling files or add re-export-only barrels.
- Keep database access in the existing domain files under `db/`. `schema.ts` is the schema source; `schema.sql` is generated by `bun db:generate` for empty databases.
- Organize each external client under `clients/<provider>/`: keep the client class and request orchestration in `index.ts`, protocol types in `types.ts`, and reusable parsing or transformation helpers in `utils.ts` when needed. Import types and helpers directly from their files; do not add re-export-only barrels or split each endpoint into its own file. Keep client-only helpers private and colocate parser tests with the parser.
- Keep background scheduling and execution in `apps/server/src/tasks/`: `index.ts` owns scheduler and worker lifecycle, `service.ts` executes queued tasks, and `errors.ts`, `types.ts`, `utils.ts` and colocated tests support that execution. This directory is not an HTTP feature module; do not create a parallel `modules/sync` or a re-export-only `tasks.ts`. Keep task persistence and management endpoints in the existing `jobs` domain.
- Do not introduce an `api/` or `handlers/` hierarchy merely to match another project. Shared utilities belong in `utils/`.
- Define business error classes in the owning feature module's `errors.ts` (or `tasks/errors.ts` for background execution) and import them directly from that file. Keep only shared error infrastructure such as `AppError` and `RemoteError` in `utils/errors.ts`. Do not define error classes inline in services or controllers, or re-export them through service files. Use type-only imports for error payload types.

## Code and frontend

- Use arrow functions for standalone functions, components and hooks. Keep class/object methods idiomatic.
- Put module-level types immediately after imports. Schema-derived aliases may stay next to their schemas.
- Use meaningful blank lines between logical steps and methods. Avoid both compressed code and arbitrary blank lines inside fluent chains.
- Keep helpers private when used in one file, below their caller when execution order allows. Extract shared helpers at the nearest appropriate location.
- Use `@page/*` and `@server/*` aliases. Browser imports from the server must be type-only. Derive HTTP contracts from Elysia and consume them through Eden.
- Keep individual React providers in `src/providers`, composed in `main.tsx`; authentication is a provider too. Queries belong in `src/hooks`, named `useSettingsQuery` and similar.
- Routes compose pages; domain forms belong in frontend modules. Reuse shadcn components and the persistent client-side layout. Do not add a parallel `pages/` directory.
- Background refreshes must preserve form drafts, focus, selection and scroll. Update only affected query data after mutations.
- UI copy should be concise and user-facing. Keep default credentials and deployment details in README; do not put implementation notes, raw diagnostic JSON, or conversational explanations in pages. Retain necessary input guidance, meaningful errors and action consequences.

## Correctness and verification

- Encrypt stored credentials, hash session tokens, and keep secrets out of source, logs and API responses. Verify authentication and cross-origin protection for management endpoints.
- Persist accepted tasks before returning success. Keep retries bounded and preserve deduplication, per-account outcomes and recovery across restarts.
- Preserve matching semantics for seasons, split cours, specials and episode offsets. Ambiguous matches require confirmation; do not weaken matching to satisfy a test.
- Colocate meaningful tests with their code. Use disposable databases and protocol-level mock transports; never modify real Plex or Bangumi state in tests.
- Check for obsolete imports, files, dependencies and docs after refactoring. Verify generated schema consistency when changing database definitions.
- Do not run Docker or browser/Playwright automation as routine verification; only do so when explicitly requested. State verification limits rather than treating unit tests as end-to-end proof.
